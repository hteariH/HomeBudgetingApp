# Family sharing

Sub-project 2 of the [self-hosted pivot](2026-10-15-self-hosted-pivot-overview.md): several
logins keep one household's books together.

## Why

The [open-source baseline](2026-10-15-open-source-baseline-design.md) already scopes every
ledger row by household, records each transaction's author, and allows several rows in
`household_members` with roles `OWNER` and `MEMBER`. What is missing is how a second person
gets into a household, what happens to the books they already had, who may manage the
membership, and the screens around it.

## Decisions

- **Joining is by invitation link.** The household's owner creates a single-use link and
  passes it on themselves (messenger, QR). It works without mail and admits the person
  even when the instance's registration is closed.
- **An existing user's books move into the household they join.** Nothing is lost; their
  old, now empty household is deleted.
- **Members are equal in the ledger.** Everyone keeps accounts, categories, transactions,
  subscriptions, currencies and bank connections alike. Only the owner invites and removes
  members, renames the household, changes its base currency, and hands ownership over.
- **One household per user**, as in the baseline. Leaving or being removed gives the user
  a new empty household of their own.

## Data model

New migration `V3__household_invites.sql` (V1 and V2 are released and no longer edited):

```sql
CREATE TABLE household_invites (
    id                 BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    household_id       BIGINT                      NOT NULL REFERENCES households (id) ON DELETE CASCADE,
    token_hash         VARCHAR(64)                 NOT NULL UNIQUE,
    created_by_user_id BIGINT                      NULL REFERENCES users (id) ON DELETE SET NULL,
    created_at         TIMESTAMP(3) WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at         TIMESTAMP(3) WITH TIME ZONE NOT NULL,
    used_at            TIMESTAMP(3) WITH TIME ZONE NULL,
    used_by_user_id    BIGINT                      NULL REFERENCES users (id) ON DELETE SET NULL,
    revoked_at         TIMESTAMP(3) WITH TIME ZONE NULL
);

CREATE INDEX idx_invites_household ON household_invites (household_id);
```

- The raw token is 32 random bytes, base64url; only its SHA-256 is stored, like auth and
  refresh tokens.
- An invite lives 7 days, is used once, and can be revoked.
- At most 10 live (unused, unrevoked, unexpired) invites per household.

`/api/users/me` gains `householdId` and `householdRole` (`OWNER` | `MEMBER`).

## Server API

Owner only (403 otherwise):

| Endpoint | Does |
| --- | --- |
| `POST /api/household/invites` body `{ "origin": "https://money.example.com" }` (optional) | Creates an invite. Returns `{ id, path: "/join?token=…", expiresAt, qrRows? }`; `qrRows` (the `QrCode.rows` format the Monobank consent screen uses) encodes `origin + path` and is present only when `origin` is given. |
| `GET /api/household/invites` | Live invites: `id`, `createdAt`, `expiresAt`, `createdBy` name. The token is never returned again. |
| `DELETE /api/household/invites/{id}` | Revokes it. |
| `PUT /api/household` body `{ "name": "…" }` | Renames the household. |
| `DELETE /api/household/members/{userId}` | Removes a member (not the owner). |
| `POST /api/household/owner` body `{ "userId": … }` | Makes another member the owner; the caller becomes `MEMBER`. |

`PUT /api/users/me/base-currency` becomes owner-only.

Any member:

| Endpoint | Does |
| --- | --- |
| `GET /api/household` | `{ id, name, baseCurrency, members: [{ userId, firstName, lastName, email, role, joinedAt }] }` |
| `POST /api/household/leave` | Leaves; refused (400) for an owner while other members remain. |

Public, for the join page:

| Endpoint | Does |
| --- | --- |
| `GET /api/invites/{token}` | `{ householdName, invitedBy, expiresAt }`. 404 for an unknown token, 410 for expired, used or revoked. |
| `POST /api/invites/{token}/accept` (signed in) | Moves the caller into the household (see below). |
| `POST /api/auth/register` with `inviteToken` | Registers even when registration is closed, and makes the new user a `MEMBER` of the invite's household instead of creating one. |

`/api/invites/**` and register-with-invite go through the same rate limiter as sign-in.

## Joining with existing books

`POST /api/invites/{token}/accept` runs in one transaction:

1. Lock both households' rows (`HouseholdRepository.lockById`) in ascending id order, the
   same lock sync pushes take, so neither a push nor a second accept can interleave.
2. Re-check the invite (live, not the caller's own household). Refuse with 400 when the
   caller owns a household that still has other members.
3. Move the caller's rows to the target household: accounts, subscriptions, transactions,
   bank connections. Categories: one with the same name, type and parent as a target
   category merges into it — its transactions and subscriptions are repointed and it is
   tombstoned; the rest move. Currency settings: union, the target's row wins on the same
   currency. Manual exchange rates: move, the target's wins on the same pair.
4. Stamp every moved or repointed row with a fresh `updated_at` from the target's sync
   clock, so other members' next pull sees it.
5. Move the membership (role `MEMBER`), mark the invite used, delete the old household.

Register-with-invite skips the move: the new user has no books.

## Leaving and removal

- Leaving or being removed creates a new household for the user (named after them, the
  family's base currency, default categories) and moves their membership there. Their
  transactions stay with the family and keep `created_by_user_id`.
- Deleting a user (self or administrator) who is the owner of a household with other
  members hands ownership to the longest-standing remaining member first. This closes the
  baseline's "ownerless household" gap.

## Web

- `/join?token=…` (public): "Anna invites you to “The Ivanovs”".
  - Signed in: "Join" with a warning that their accounts and history will move into the
    family; on success, to `/app`.
  - Signed out: register through the invite (works with closed registration) or sign in
    and come back to the same page.
  - Expired, used or revoked: a clear message; unknown: "this link does not work".
- `/app/household` ("Family" in the menu): members with role and joined date; "Leave".
  For the owner also: "Invite" (link with copy and the QR from `qrRows`), live invites with
  revoke, rename, remove member, make owner.
- Transactions: when the household has more than one member, each row shows its author's
  initials, and the filters gain "Who".

## Android

- "Family" under More: members, and "Invite", which opens the system share sheet with the
  server address plus the invite path. Accepting happens in the browser: an app cannot
  claim links on an arbitrary self-hosted domain.
- Household change: the app compares `householdId` from `/api/users/me` with the one it
  stored. When it differs (joined, left, removed), it clears the local database, resets the
  sync cursor and pulls everything, with no confirmation — the data is on the server — and
  shows once "You are now in the household “…”".
- Sync carries `createdByUserId` on transactions (Room migration 4 → 5 adds the column).
  Names come from the cached `/api/household` members. Initials show only when there is
  more than one member.

## Errors

| Case | Answer |
| --- | --- |
| Unknown token | 404, no hint whether it ever existed |
| Expired, used or revoked token | 410 with the reason |
| Accepting an invite into one's own household | 400 |
| Owner of a household with other members accepts or leaves | 400: transfer ownership or remove members first |
| More than 10 live invites | 409 |
| A member calls an owner-only endpoint | 403 |

## Testing

Server:

- Invite lifecycle: create, preview, single use, expiry, revoke, the 10-invite cap.
- Register with an invite while `REGISTRATION=closed`: becomes `MEMBER`, no own household.
- Accept with existing books: accounts, transactions and subscriptions moved; a same-named
  category merged with its transactions and subscriptions repointed; currency settings and
  manual rates resolved as specified; old household gone; a pull from `EPOCH` by another
  member sees the moved rows.
- Leave and remove: new empty household with defaults; their transactions stay with the
  family with the author kept; a former member no longer sees family data (an isolation
  case added to `HouseholdIsolationTest`).
- Ownership transfer; owner-only endpoints refuse members; deleting an owner with members
  hands ownership on.
- Accept and sync push in parallel on the same households finish without deadlock.

Web: `/join` signed in, signed out and expired; the Family page as owner and as member;
author initials and the "Who" filter appear only with more than one member.

Android: household change triggers clear and full pull; Room migration 4 → 5 (alongside the
existing `MigrationTest`); initials only with more than one member.

## Out of scope

- Several households per user and switching between them.
- A read-only role.
- Invitations bound to an email address, and sending invitations by mail.
- Per-member budgets or analytics.
